# Server shutdown and update handoff

- The maintenance loop checks for at least one living, non-spectator player. Once a human player has joined, the server shuts down when none remain. The check runs every 200 ms; an untouched server with no players does not shut itself down at startup.
- A source change is detected by comparing the startup fingerprint of JavaScript files and package manifests when `SIGINT` or `SIGTERM` arrives. A replacement process writing a new PID to `serv.lock` is also treated as an update signal. Hosts that provide an explicit reason can set `RANAR_SHUTDOWN_REASON=update` or `RANAR_UPDATE_SHUTDOWN=1`.
- During an update handoff, the old process broadcasts `Closing the server for updates.` and releases its HTTP listening socket, but keeps its simulation and existing WebSocket clients running while the replacement starts. It does not close the arena yet.
- Once the replacement is listening and writes the matching readiness marker, the old process begins its normal arena-closing sequence. It closes the arena to new joins and spawns the four Living Apocalypses in the old process. If players remain, the existing 30-second closing/disconnection window runs; if no players remain, it can finish immediately after spawning them. Only after that sequence completes does it stop simulation, disconnect its remaining clients, and exit. If the arena-close sequence had already begun before the update signal, any not-yet-spawned Living Apocalypses and the final disconnect step are deferred until replacement readiness.
- `RANAR_UPDATE_HANDOFF_TIMEOUT_MS` controls the safety timeout (default 30000 ms; values below 5000 ms are raised to 5000 ms). If the replacement never becomes ready, the old process closes rather than remaining stuck indefinitely.
- A real overlap handoff requires the hosting platform to start the replacement process while the old process is still alive and to share the project directory. If the platform only starts a replacement after the old process exits, the safety timeout is used and a true zero-gap handoff is not possible from this application alone.
- The old instance writes a score snapshot when the replacement becomes ready and refreshes it immediately before disconnecting. Each connected player's score is persisted under the combination of IP address and normalized player name; recently disconnected players whose bodies are still in the normal reconnect cache are included too. The replacement reloads the recovery file before consuming an entry, so it can see the final snapshot even though it started earlier. A matching player can reclaim that score once within five minutes. Used entries are removed immediately; all remaining entries expire and the file is deleted after the recovery window. Fatal errors also capture scores; ordinary shutdowns do not.
- Natural empty-server shutdown and unexpected errors do not create update score-recovery entries and do not display the update message.
